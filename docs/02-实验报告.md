### 3.2 修改主机名为姓名全拼并同步 /etc/hosts

**诊断现状：**

```bash
cat /etc/os-release
hostnamectl
cat /etc/hosts
```

**备份后修改：**

```bash
cp -a /etc/hosts /etc/hosts.bak.$(date +%F)
cp -a /etc/hostname /etc/hostname.bak.$(date +%F)
hostnamectl set-hostname wangqi
sed -i 's/\b127\.0\.1\.1.*/127.0.1.1\twangqi/' /etc/hosts
grep -q "127.0.0.1.*wangqi" /etc/hosts || echo -e "127.0.0.1\twangqi" >> /etc/hosts
```

**验证（含重启后）：**

```bash
hostnamectl | grep -i "static hostname"
getent hosts "$(hostname)"
reboot
# 重连后再次执行上述两条
```

【截图 2：`hostnamectl` 显示 Static hostname: wangqi】
【截图 3：重启后 `hostname` + `getent hosts` 输出】

原理说明：`hostnamectl` 修改的是 `/etc/hostname`（静态主机名，重启后仍生效）并同步内核运行态主机名；而 `/etc/hosts` 是名称解析用的，Ubuntu 默认用 `127.0.1.1 <主机名>` 映射本机名，不同步会导致 `sudo` 报 `unable to resolve host`——报错但功能正常，容易忽略。

**配置反向代理：**

```bash
cp deploy/nginx-finalwq.conf /etc/nginx/sites-available/finalwq.conf
ln -sf /etc/nginx/sites-available/finalwq.conf /etc/nginx/sites-enabled/finalwq.conf
rm -f /etc/nginx/sites-enabled/default
nginx -t && systemctl reload nginx
```

配置要点（`deploy/nginx-finalwq.conf`）：

```nginx
location /static/ { alias /root/FinalWQ/static/; }
location / {
    proxy_pass http://127.0.0.1:8000;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}
```

## 五、遇到的问题与排查

**问题 1：`nginx -t` 报 `bind() to 0.0.0.0:80 failed (98: Address already in use)`**

- 排查：`ss -tlnp | grep ':80'` 发现 80 端口被先前手工启动的 nginx 进程占用；`systemctl status nginx` 只显示"failed"，真实原因在 `journalctl -u nginx` 里。
- 处理：`systemctl stop nginx && pkill -f 'nginx: master'` 后重启。根因是重复启动，不是配置错误。
- 收获：**`systemctl status` 的摘要是结论，不是证据**，必须往下看 `journalctl`。

**问题 2：改了 hostname 后执行 `sudo` 报 `unable to resolve host wangqi`**

- 排查：`getent hosts wangqi` 无输出，`cat /etc/hosts` 里仍是旧主机名。
- 处理：补 `127.0.1.1 wangqi`。根因是 Ubuntu 用 `127.0.1.1` 映射本机名，`hostnamectl` 不会替你改这一行。
- 收获：主机名是"两处状态"——`/etc/hostname`（标识）与 `/etc/hosts`（解析），必须同时改。

**问题 3：页面能打开但样式全丢（CSS 404）**

- 排查：`curl -I http://IP/static/css/style.css` 返回 404；Nginx error.log 显示 `open() ".../static/css/style.css" failed`。
- 处理：`location /static/` 的 `alias` 末尾斜杠与实际目录不一致，修正为 `/root/FinalWQ/static/`。
- 收获：Nginx 的 `alias` 对结尾斜杠敏感，`root` 是拼接、`alias` 是替换，两者语义不同。

## 六、总结反思

1. **部署链路的每一层都要能单独验证**。这次最有用的习惯是"分段验证"：先 `curl 127.0.0.1:8000` 证明 Django 活着，再 `curl 127.0.0.1` 证明 Nginx 反代活着，最后 `curl 公网IP` 证明安全组放行。出问题时能立刻定位到哪一段断了，而不是盲改配置。

2. **"能跑"和"可维护"是两件事**。一开始我也可以直接 `nohup python3 manage.py runserver` 了事，但进程挂了没人拉起、重启机器就没了。换成 systemd + `Restart=always` 之后，服务具备自愈能力；`LimitNOFILE` 这类参数也只有在 systemd 里才能生效（`limits.conf` 对它无效）。

3. **工程脚手架的价值在"约束"而非"方便"**。虚拟环境约束解释器、pylint 约束代码风格、pytest 约束行为，三者让"改一行代码"不至于悄悄破坏别的地方。`make all` 一条命令跑完，比记四条命令可靠。

4. **关于 AI 功能本身的一点反思**：我在实现中刻意加了"置信度阈值转人工"和"必须带引用来源"两条硬约束。原因是诊断类应用的成本不对称——答错一条会删数据的命令，代价远高于回答"我不确定"。这也让我理解了课上讲的"AI 不是替代判断，而是把人的判断力放大到更多场景"。

5. **不足与改进**：目前规则库是静态的，新增故障需要改代码；下一步可以把知识库迁移到数据库 + 后台管理，让教师直接维护；另外诊断结果只做文本展示，未来可以加"一键复制命令"和执行前的高危二次确认。
