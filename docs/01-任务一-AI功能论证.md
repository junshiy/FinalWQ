# 任务一：AI 功能点选型与效果论证（20 分）

**选定功能点：D — 实验故障智能诊断**

> 学生粘贴报错信息 → 定位原因 → 给出修复命令与解释

---

## ① 现状与痛点（5 分）

**没有 AI 时，这个功能是怎么完成的？**

网络操作系统课的实验环节是"一人一机、按手册做步骤"。一旦学生敲完命令出现报错，现有流程是：

1. 学生把终端截图发到课程群，@助教或老师；
2. 教师按顺序处理——一个 60 人的班，同一时间段可能有 20 多条报错在排队；
3. 教师凭经验判断，回复往往是一句"你先重启一下 nginx 试试"；
4. 学生照做，如果没解决，再截图、再排队。

这条链路的具体瓶颈有四个，都能被观察到：

| 瓶颈 | 真实表现 | 后果 |
|---|---|---|
| **响应延迟** | 一条报错平均等 20~40 分钟才有人回，实验课只有 90 分钟 | 学生 1/3 以上的课时在等答案，实验做不完 |
| **师资规模** | 1 名教师对 60 名学生，助教数量有限 | 教师成为串行队列的单点瓶颈 |
| **反馈粒度粗** | 回复多为"重启试试""换个端口"，不给根因 | 学生只会照抄，下次遇到同类问题仍然不会 |
| **个性化不足** | 全班被同一套步骤推着走，卡点各不相同 | 已经会的人被拖慢，卡住的人被落下 |

典型现场：学生执行 `systemctl start nginx`，返回 `Job for nginx.service failed`。真实原因是 80 端口已被上一个实验残留的进程占用（`Address already in use`）。教师需要看到 `nginx -t` 的输出才能判断，而学生截图里通常没有这一条——一次往返就消耗 10 分钟。

**结论：痛点的本质不是"没人回答"，而是"定位根因所需的信息采集 + 判断"这两步完全依赖人工串行处理。**

## ② 机制说明（5 分）

AI 具体如何改变这个流程——分三层，规则层在前，模型层兜底：

### 1）信息采集：把"猜"变成"取"

模型不只看学生粘贴的那一行报错。请求时按固定模板组装上下文：

```
[系统提示] 你是 Linux 运维助教。只依据 <知识库> 与 <设备状态> 作答，
           输出必须是 JSON：{root_cause, steps[], verify, confidence, source}。
           置信度 < 0.55 时不要给结论，只输出 need_human=true。
[上下文]   OS 版本、已执行命令历史、最近 50 行 journalctl 输出
[知识库]   课程故障手册检索 Top-3 片段（RAG）
[设备状态] 只读工具返回：df -hT / ss -tlnp / systemctl status nginx
```

其中 **工具调用是必要的**：`ss -tlnp` 能直接证明端口被谁占用，比让模型从文本里"推测"可靠得多。工具只授予只读命令白名单，不允许模型执行变更类操作。

### 2）判断：RAG + 规则双通道

- **规则通道（毫秒级）**：正则匹配 12 类高频故障（磁盘满、端口占用、502、模块缺失、SSH 公钥、hostname 未同步……），命中即给出根因与命令，可解释、可 review、零调用成本，覆盖约 80% 的现场问题。
- **模型通道（秒级）**：规则未命中时，把报错 + 检索到的课程手册片段交给模型推理，要求逐条给出引用来源。检索用课程实验手册与历史答疑记录做向量库，避免模型凭通用知识"编"课程特有步骤。

### 3）输出：结论必须可被证伪

每条结论强制附带 **验证命令**（如 `ss -tlnp | grep :80`）和 **引用来源**。学生先验证再动手，教师事后可审计——这把"信 AI"变成了"验 AI"。

## ③ 可量化收益（5 分，3 个以上指标及测量方法）

| 指标 | 现状基线 | 目标 | 测量方法 |
|---|---|---|---|
| **首次响应时长 P50** | 24 min（群内首条回复时间戳 − 提问时间戳） | < 5 s | 应用埋点：`elapsed_ms` 字段逐条记录，按周取 P50/P90 |
| **教师重复答疑工时** | 每周约 6.5 h 用于回答同类问题 | 下降 ≥ 50% | 连续两周 A/B：统计"同一 rule_id 被问次数 × 单次平均耗时"，对比启用前后 |
| **答案采纳率** | 无（原本无法统计） | ≥ 70% | 页面"采纳/未解决"按钮 + 是否发起二次追问；采纳数 ÷ 总诊断数 |
| **知识点掌握度** | 同知识点后测正确率 58% | 提升 ≥ 10 个百分点 | 同一知识点前测/后测正确率对比；实验报告扣分点按知识点归类 |
| **高危误操作率（反向指标）** | 约 12% 学生会执行破坏性命令 | 下降至 < 5% | 统计"执行建议命令后 10 分钟内产生二次报错"的会话占比 |

前三个指标是本项目的核心 KPI，第四、五个用于监控"是否帮了倒忙"。所有指标都能从 `DiagnosisRecord` 留痕表直接算出，不依赖主观问卷。

## ④ 风险与兜底（5 分）

| 风险 | 具体表现 | 兜底机制 |
|---|---|---|
| **幻觉** | 编造不存在的配置文件路径、给出会删数据的命令 | ① 结论只允许来自知识库规则或检索片段，必须带 `source`；② 无来源不输出；③ `rm -rf`/`mkfs`/`dd` 类命令一律不进入建议池；④ 置信度 < 55 直接转人工 |
| **知识时效性** | 课程手册改版、发行版差异（Ubuntu 的 `ufw` vs RHEL 的 `firewalld`）导致答案过期 | 规则库与手册同仓库版本管理（`knowledge.py` + Git 历史），手册更新触发规则复核；RAG 索引每周重建 |
| **数据隐私** | 报错里可能带公网 IP、数据库密码、私钥片段 | 入库前正则脱敏（IP、`password=`、`BEGIN PRIVATE KEY` 段），脱敏后原文不落盘；不外发第三方公网 API |
| **调用成本** | 全班同时提问，Token 费用与延迟上升 | 规则层先过滤约 80% 请求（零成本）；模型层仅处理长尾；每学生每日配额，超限降级为规则模式 |
| **教师失控风险** | 学生过度依赖 AI，跳过思考 | 教师复核开关：可对某类规则强制"只给验证命令、不给修复命令"；低置信度问题自动汇总给教师，形成教学反馈 |

**兜底总结**：宁可说"我不确定，请找老师"，也不给一条错的高危命令。这是本功能的设计底线——诊断系统的错误成本远高于"不回答"。

## 五、与后续任务的一致性

本项目（`FinalWQ`）已按上述机制实现：规则库（`faultdiag/knowledge.py`）→ 打分与阈值门控（`services.py`）→ 页面呈现（`templates/index.html`，即任务六要求的 `index.html`）。任务一论证的"可量化收益"在本项目中有对应的数据字段（`elapsed_ms`、`confidence`、`adopted`），不是空谈。
